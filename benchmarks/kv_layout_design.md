# 从选择记录重放到 KV 布局预排

日期：2026-10-31。**设计假设，尚未实现或计时。**

用户补充：既然同前缀重放时已经知道后续会访问哪些位置，就可以提前设置专门的连续槽位块，使 attention 更方便地从显存按 tile 搬入片上 shared memory / SRAM。这里的“整块拉入”重点是 **HBM → 片上存储**，不是仅把 CPU → GPU 传输合并。

## 建议的数据布局

对一层的一组 G 个 query，解码各自的原始选集 S_q，计算并集 U，并建立逻辑 KV 块到紧凑槽位的映射。只将并集中的 KV 各收集一次，按 attention 内核需要的维度顺序、对齐和 tile 大小写入 HBM 工作区；每个 query 保存自己的局部索引或位图。

```text
已缓存的逻辑选集 ──→ 分组并集 + 局部索引 + 搬运计划
                              │
有效 KV（HBM 或 host） ──→ 连续 HBM 槽位 A/B
                              │ 按 tile 搬入
                         shared memory
                              │ 使用各行自己的 mask
                         原稀疏 attention
```

这与现有 union-bitmap 索引编码有直接联系：字典中的逻辑块可以成为 KV 工作区的槽位顺序，位图可以描述每个 query 的支持集合。不过当前 CUDA 解码器只恢复逻辑 ID，没有实现 KV gather、布局转换或消费此布局的 attention 内核。

**不能让组内所有 query 都 attend 整个并集。** 各行仍只使用 S_q，保留因果位置、有效长度、位置偏置及 padding 语义。按并集 tile 计算再 mask 可能增加无效 QK 运算；按局部列表计算则仍存在一定间接访问。两者需要按重合率和实际 kernel 比较。索引重排也可能改变浮点归约顺序，不能只凭集合相等声称逐 bit 输出相同。

连续 HBM 槽位并不意味着整个工作集都放入 SRAM。shared memory 容量和 occupancy 要求分 tile、分阶段搬运；只有 attention 内核真正利用该布局，才可能获得更规整的访存和跨 query 复用。单独分配连续张量不会自动改善现有 paged/sparse kernel。

## 与 HiSparse 的连接点

[HiSparse 论文](https://arxiv.org/html/2608.07009v1)已有固定大小 GPU 热 KV 缓存、逻辑位置映射及缺失换入；[SGLang 官方文档](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/hisparse_guide.mdx)还描述了共享 indexer 场景下提前重放后续层的搬运计划。其主要目标是控制 decode 的 KV 驻留容量；本设计提出的新增用途是利用已缓存前缀的未来访问集合，提前为消费内核组织 HBM 布局。不能把“紧凑 GPU 槽位”或“预取”本身当作新的发明。

可先比较两种组合方式：

1. **保留 HiSparse 热缓存，另设小型连续 attention 工作区。** 数据来源可包含已有 GPU hits 和 host misses，容易隔离验证，但要付出 gather、写入和额外容量。
2. **在换入时直接填入计划好的消费槽位。** host miss 的换入和布局整理合为一步，避免先换入再复制；但 GPU hits 可能仍需搬动，而且未来要保留的热点会与连续分组布局冲突。不能为了连续性每步搬空热缓存。

只缓存逻辑搬运计划，不跨请求复用旧的物理 GPU 地址；每次运行根据当前页表重新绑定，并用 ready/consumed 事件保护槽位生命周期。不同层的 KV 数值不同，不能因选集相同就共享 KV 内容。

重放已知的是**相同完整因果前缀中已记录的 query**。它不自动知道新生成 token 的下一步选集；新后缀仍运行 selector，除非模型本来就保证跨层共享。若旧主 KV 已彻底丢弃，预排只能提前确定目的位置，实际搬运仍需等待本轮对应层的 KV 被重建；若 host 保有有效完整 KV，则可以更早加载，这属于另一种缓存状态，必须分别评测。

## 进一步控制重复 prefill 的 KV 显存

如果绝大部分主 KV 保存在 CPU，且相同前缀的后续选择记录已知，可以按下一次使用的截止时间预取，仅在 HBM 留下当前 query 组的并集、少量未来组和有价值的重复热点。已知完整重放窗口还允许按未来使用距离规划淘汰，而不必只靠 LRU。这里是离线访问序列可用时的调度机会，不是已经实现的算法。

可用一个容量目标描述：

`M_KV_HBM ≈ sum_over_live_layers(B_KV_block × resident_blocks) + staging`

resident_blocks 由当前并集、预取深度、保留热点和槽位预算共同决定，可以小于整个 N-token 历史。它不等于单个 query 的 top-k；不同 query 的并集可能迅速变大。预算不足时可以缩小 query 组，或用能在多个 KV tile 间保持正确 softmax 累积的 attention 路径，但会改变吞吐和调度成本。

为降低 **prefill 峰值**，还必须采用合适的分块执行，避免先物化整段 Q/K/V 或整段中间激活，再进行 offload。多层同时保留的 KV、权重、压缩 indexer keys、线性/循环状态、请求元数据和算子 workspace 要独立计量；选择记录的流式缓冲也单独计入。

就绪条件包含两件事：需要的 KV 数值已经存在，以及传输在消费前完成。若 CPU 已有有效 KV，可直接预取；若原 KV 已全部淘汰，本次重算产出后才能备份/搬运，不能只凭选集提前恢复数值。用完的旧 KV 对未记录的新 query 仍可能有价值，通常需要在 host 保留完整后备，不能因它在当前重放窗口不再使用就永久丢弃。

预取不能消除流量。稳态平均搬运需求必须不超过实际可用带宽，还需测首次等待、D2H 备份、双向链路争用和 CPU 容量。因此可验证的主张是“降低主 KV 的 HBM 驻留并测出延迟代价”，而不是“任意小显存且无延迟增加”。普通第一次 prefill 无完整历史选择记录时，需要另列基线。

## 何时可能划算

设每个逻辑 KV 块有 B 字节，组内并集大小为 U。独立整理一个 HBM 工作区至少新增约 U·B 的源读取和 U·B 的目标写入，另计后续 attention 读取；不能只计整理后的 kernel 时间。G 个 query 的名义 KV 需求是 G·k·B，但原始 kernel 的 L2/shared-memory 复用可能已经消除了部分重复读取，因此不能把 G·k/U 直接当作加速比。

最有希望的情形是较多 query 共享小并集、原布局分散且当前 kernel 复用差、已有 KV 换入能顺便完成布局整理，或者整理可以与前面的计算重叠。单个 query、低重合率、已有良好块连续性或 L2 命中时，额外复制可能更慢。预取与 attention 争用 HBM 带宽也可能让“被隐藏”的准备工作拖慢前段。

端到端判据是：可见的计划/整理/等待开销，加上新布局 attention 时间，小于原始布局 attention 时间；同时检查整体 prefill / TTFT，而非只看 attention kernel。

## 最小实验矩阵

固定同一批 Q/K/V、同一选集与精度，比较：原布局间接访问；已知选集但不重排；预排连续工作区；换入直接填连续槽位。分别测试缓存重放命中与正常新 query，保留原生 HiSparse 作为可用架构上的对照。

- G=1/8/16/32，记录真实 U/k、各 query 重合率和重复搬运字节；用真实轨迹加低相关对照。
- 测完整路径时间、整理时间、attention 时间、真实 HBM 读写、L2 命中、shared-memory/寄存器占用和 GPU 临时容量。
- 将双缓冲容量与准备提前量作为变量；先测 HBM 已有 KV，再独立测 host 换入，避免混淆两条收益来源。
- 验证每行支持集、索引映射、位置/mask、数值和生成输出；低重合率或准备来不及时回退原路径。
